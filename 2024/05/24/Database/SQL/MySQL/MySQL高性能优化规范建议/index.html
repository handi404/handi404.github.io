MySQL 高性能优化规范建议

本文最后更新于 2025年8月1日 晚上

我将从五个层面展开，由内到外，覆盖从表设计到架构的全链路优化：

  1. 数据库设计规范 (Schema Design)
  2. 索引设计与使用规范 (Indexing)
  3. SQL 编写规范 (Query Writing)
  4. 事务与锁规范 (Transaction & Locking)
  5. 架构与配置规范 (Architecture & Configuration)

1. 数据库设计规范 (Schema Design)

设计是性能的基石。糟糕的设计，后期再多优化技巧也只是杯水车薪。

核心原则：三少一范式

  • 少关联： 尽量减少表之间的关联，尤其是在核心交易链路上。过多的 JOIN 会让查询变得复杂且低效。
  • 少字段： 单表字段不宜过多（建议不超过 50 个），特别是 TEXT/BLOB 等大字段。将大字段或不常用字段拆分到扩展表，是垂直拆分的基本功。
  • 少依赖： 避免在数据库中使用外键约束。虽然外键能保证数据完整性，但在高并发场景下，它会成为性能瓶ICC，增加数据库的负担。建议将数据一致性的校验放在应用层完成。
  • 遵范式： 严格遵循三大范式（3NF）进行基础表设计。但在某些查询场景下，可以适度反范式（冗余字段），以空间换时间，避免不必要的 JOIN。

规范细则：

  1. 数据类型选择：

    • 用最“窄”的类型： 优先使用能容纳数据的最小类型。例如，能用 TINYINT 就不用 INT，能用 VARCHAR(50) 就不用 VARCHAR(255)。这能减少磁盘空间、内存占用和网络I/O。
    • 数字优于字符串： 如果一个字段只存储数字，就用数值类型，其查询和计算性能远超字符串。
    • DECIMAL 用于金钱： 涉及金额、费率等精确计算的场景，必须使用 DECIMAL，严禁使用 FLOAT 或 DOUBLE，避免精度丢失。
    • 时间类型： 推荐使用 TIMESTAMP 或带时区的 DATETIME (DATETIME(6) 可支持微秒)。TIMESTAMP 存储占用更少，且自带时区转换功能。

  2. 避免 NULL：

    • NOT NULL 是金科玉律： 尽量将所有列定义为 NOT NULL，并提供一个有意义的默认值（如 0、空字符串 '' 或特定值 -1）。
    • 为什么？
      • NULL 值的列使索引、索引统计和值比较都更复杂。
      • COUNT(字段) 时，NULL 值不会被计算在内，容易引入 bug。
      • 可读性差，IS NULL 或 IS NOT NULL 的判断不直观。

  3. 字符集统一：

    • 统一使用 utf8mb4： 这是事实上的标准。utf8mb4 是 utf8 的超集，能完美支持 Emoji 表情和各种生僻字。不要再使用 utf8（它最多只支持3字节的UTF-8编码）。
    • 校对规则： 一般使用 utf8mb4_general_ci（不区分大小写，速度快）或 utf8mb4_unicode_ci（更准确，但稍慢）。

2. 索引设计与使用规范 (Indexing)

索引是提升查询速度最直接、最有效的手段。

核心原则：为查询而生，精准覆盖

  • 为 WHERE, JOIN, ORDER BY 的列建索引： 这是索引设计的第一出发点。
  • 精准覆盖： 只索引需要用到的列，不要建大而无当的索引。
  • 不滥建： 索引会增加写操作的开销（INSERT/UPDATE/DELETE）并占用磁盘空间。

规范细则：

  1. 最左前缀原则 (Left-Prefix Principle)：

    • 这是联合索引的灵魂。对于一个联合索引 (a, b, c)，它相当于创建了 (a)、(a, b)、(a, b, c) 三个索引。
    • 查询必须从索引的第一个字段开始，且不能跳过中间字段。
      • WHERE a=1 AND b=2 ✅ (用上 a, b)
      • WHERE a=1 AND c=3 ❌ (只用上 a)
      • WHERE b=2 AND c=3 ❌ (完全用不上)

  2. 区分度 (Cardinality) 是关键：

    • 选择区分度高的列作为索引。像“性别”这种只有两三个值的列，建索引几乎没有意义，因为优化器很可能选择全表扫描。
    • 使用 COUNT(DISTINCT a) / COUNT(*) 来评估列的区分度。

  3. 拥抱覆盖索引 (Covering Index)：

    • 定义： 一个查询需要的所有数据，都能从一个索引中直接获取，无需再回表查询主键索引。这是性能优化的终极利器之一。
    • 实践： 在 SELECT 后只列出必要的字段，并确保这些字段（以及 WHERE 中的字段）都被包含在一个联合索引中。
    • 识别： 使用 EXPLAIN 分析查询计划，如果 Extra 列显示 Using index，即表示命中了覆盖索引。

  4. MySQL 8.0+ 新特性：

    • 函数索引 (Functional Indexes)： 可以直接对表达式或函数结果创建索引。例如，对 JSON 列中的某个字段建立索引。
    • 降序索引 (Descending Indexes)： 在 8.0 之前，DESC 只是语法糖，实际还是按升序存。8.0 之后，可以真正创建降序索引，对 ORDER BY ... DESC 的查询有优化。

  5. 索引维护：

    • 定期使用 pt-duplicate-key-checker 等工具检查和清理重复、冗余的索引。

3. SQL 编写规范 (Query Writing)

写出高效、优雅的 SQL 是每一位开发者的基本素养。

核心原则：简单、直白、避免“索引杀手”

  • SQL 要简单： 一个 SQL 只做一件事。复杂的逻辑拆分到多个 SQL 或在应用层处理。
  • 避免隐式转换： 确保 WHERE 子句中，列的类型和值的类型完全匹配，否则可能导致索引失效。
  • 拥抱 EXPLAIN： 对任何不确定的、复杂的查询，都必须先用 EXPLAIN 分析其执行计划。

规范细则（索引杀手黑名单）：

  1. 严禁 SELECT *：

    • 增加网络 I/O 开销。
    • 无法命中覆盖索引。
    • 增加应用代码的脆弱性（表结构变更时）。

  2. WHERE 子句避免对列使用函数或运算：

    • 错误示范： WHERE DATE_FORMAT(create_time, '%Y-%m-%d') = '2023-01-01'
    • 正确示范： WHERE create_time >= '2023-01-01' AND create_time < '2023-01-02'
    • 原理：保持列的“纯净”，让数据库能直接使用索引进行范围查找。

  3. LIKE 查询注意：

    • LIKE '%keyword' 或 LIKE '%keyword%' 无法使用索引。
    • LIKE 'keyword%' 可以使用索引。

  4. OR 的使用：

    • 在 WHERE 子句中，OR 连接的条件如果其中一个没有索引，通常会导致整个查询索引失效。可以考虑用 UNION ALL 替代。

  5. 分页优化：

    • 错误示范 (深度分页性能雪崩)： LIMIT 1000000, 10

  6. IN vs EXISTS：

    • 遵循“小表驱动大表”原则：当子查询结果集较小时，用 IN；当外表较小时，用 EXISTS。

4. 事务与锁规范 (Transaction & Locking)

高并发场景下，事务和锁是性能瓶颈和死锁的重灾区。

  1. 事务要小而快：

    • 大事务是万恶之源。 事务应尽可能缩短，只包裹必要的核心写操作。
    • 避免在事务中包含 RPC 调用、复杂的计算或耗时长的操作。

  2. 依赖 InnoDB 的行级锁：

    • 不要手动执行 LOCK TABLES，这会锁住整张表，极大降低并发能力。
    • 对于需要锁定读取的场景，使用 SELECT ... FOR UPDATE。但要清楚它会施加行级排他锁，必须在事务中，且尽快提交。

  3. 降低死锁概率：

    • 保持一致的加锁顺序。
    • 使用合理的索引，不合理的索引会扫描更多行，增加锁冲突。
    • 缩短事务。

5. 架构与配置规范 (Architecture & Configuration)

  1. innodb_buffer_pool_size 是核心：

    • 这是 InnoDB 最重要的配置参数，它缓存了数据和索引。
    • 建议设置为物理内存的 50% ~ 70%（对于专用的数据库服务器）。

  2. 使用连接池：

    • 应用层必须使用数据库连接池（如 HikariCP, Druid），避免频繁创建和销毁连接的开销。

  3. 读写分离：

    • 对于读多写少的场景，部署主从复制，使用读写分离架构。写操作走主库，读操作走从库，分散压力。
    • 注意： 读写分离会带来数据延迟问题，需要业务能容忍。对于实时性要求高的读，仍需访问主库。

  4. 硬件是基础：

    • 使用 SSD 硬盘，其随机 I/O 性能是机械硬盘的数百倍，对数据库性能是质的提升。
